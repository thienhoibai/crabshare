# CS-74 / VI-15 Backend Core Design

## Goal and phase boundary

Implement the backend foundation for printing and activating harvest tags, replacing an invalid tag, and preventing invalid tags from being recognized during trace lookup. The first phase covers the API, persistence, Evidence Reviewer decision path, and server-side trace behavior. Web printing and mobile capture/list screens follow in a later phase.

The label output contains the existing tag code and a trace URL. It does not control or verify physical printer hardware. Tag codes continue to come from VI-14 and are never regenerated by a label read.

## Existing behavior and constraints

- VI-14 creates one `Printed` tag for each harvested crab. Codes are 12 characters from `23456789ABCDEFGHJKMNPQRSTUVWXYZ`; the unique code constraint and filtered one-non-void-tag-per-crab index already exist.
- Harvest releases the crab's box allocation. KH-07's current upload endpoint only accepts a live, occupied allocation, so the post-harvest confirmation photo needs a supported capture context tied to the harvested crab.
- Evidence is stored as `Photo` with source `InAppCapture`. Upload assigns `Accepted`, `Watch`, or `Flagged`. Evidence Reviewers can currently decide only `Flagged` evidence; `Pass` maps to `Accepted`, `Fail` to `Rejected`, and `NeedMoreEvidence` to `Flagged`.
- `crab_tag` already has `activation_evidence_id`, an FK to `evidence`, and a CHECK requiring both activation time and evidence for `Active`. Do not edit the applied V001 migration. Verify the active database has the equivalent constraints; add a forward-only migration only if that verification finds a missing constraint.
- There is no tag API controller or trace API implementation yet. The web trace route is a placeholder. The existing `v_traceability` view includes tag status and activation photo data, so API code must filter before exposing any trace payload.
- `crab_item_event` already supports `TagActivated` and `TagVoided`, including tag, evidence, actor, and time references.

## API and domain behavior

### Operator tag list and label

- Add a paged `GET /api/tags?status=Printed&page=1&pageSize=20`, scoped to the authenticated Operator Owner/Staff and their approved Operator. The endpoint supplies the mobile client with unactivated tags without scanning labels one by one.
- Add `GET /api/tags/{tag}/label`. Return the existing tag code, configured absolute trace URL, and only product details already approved for the label. A `Void` tag is not printable as valid; viewing a label never activates it.
- Add a configured public trace base URL. Join it with `/truy-xuat/{tag}`; do not use the API host, hard-code a domain, or hard-code localhost.
- Both reads verify current database membership and ownership of the tag's Operator, not only role claims in the JWT.

### Evidence capture and review

- Extend the existing `POST /api/evidence` multipart contract with an optional `tagCode` field for harvest confirmation. When provided, the service resolves the tag, checks that the current user manages its Operator and that the tag is `Printed`, then obtains the batch, box, and crab from the tag relationship. Capture therefore remains within KH-07 storage, image validation, hashing, duplicate detection, risk scoring, and audit behavior even though the harvest released the box.
- Persist a nullable crab-item reference on evidence for this harvest context, with an FK. Existing evidence remains unlinked. The reference is not unique: multiple photos may refer to a crab, and no one-evidence-per-tag constraint is introduced. Activation verifies the evidence refers to the same crab as the tag.
- Activation eligibility requires a real `Photo`, `InAppCapture`, matching crab/batch/Operator context, and `Accepted` status. Missing, foreign, stale/unaccepted, non-photo, and rejected evidence cannot activate a tag.
- An evidence upload automatically marked `Watch` or `Flagged` must be handled by an Evidence Reviewer before activation. Extend the existing reviewer decision path so `Watch` can be reviewed. `Pass` sets `Accepted`, `Fail` sets `Rejected`, and `NeedMoreEvidence` remains `Flagged`. Preserve the current reviewer investment-conflict check, decision notes, concurrency behavior, and audit trail. Operators cannot set evidence status themselves.

### Activation

- Add `POST /api/tags/{tag}/activate` with `{ "evidenceId": 123 }`.
- In one serializable transaction, lock using the existing audit convention; verify current Operator access, `Printed` tag state, same-crab eligible evidence, then set `Active`, `activation_evidence_id`, activation time, and actor according to the current schema/conventions. Add `TagActivated` event and audit record in the same transaction.
- Repeating activation with the same evidence is idempotent and creates no duplicate event. Repeating with a different evidence ID after activation returns a conflict and cannot replace the recorded photo.
- Preserve evidence reuse capability where the same evidence still refers to the same crab; do not add a uniqueness constraint on `activation_evidence_id`.

### Void and replacement

- Add `POST /api/tags/{tag}/void` with `{ "reason": "..." }`. Trim and validate the reason using existing conventions; store the reason, actor, and timestamp.
- In the first phase, void/replace is allowed for `Printed` or `Active` tags only while the crab item is `InStock`. Require Operator Owner permission. In one transaction, mark the old tag `Void`, create a new `Printed` tag for the same crab with a fresh VI-14 code, append tag events, and write audit records. The replacement has no inherited activation evidence.
- Keep existing unique-code and one-non-void-tag constraints. Reuse the VI-14 code generator and its collision retry behavior. Repeated requests cannot create multiple replacements; an already-void tag does not start another replacement operation.
- Labels and trace lookups for a void code never redirect to the replacement code.
- **TODO for a later phase:** define the exceptional process for voiding/replacing an `Active` tag after the crab has been `Packed` or `Delivered`, including how order and trace history should represent the replacement. This phase rejects those requests.

### Trace lookup

- Add the public `GET /api/trace/{tag}` API used by `/truy-xuat/{tag}`.
- Only `Active` tags return the trace payload. `Void` returns a clear `tag.void` response (“Tem đã bị hủy”) without trace details. `Printed` returns no product trace data until activation. Unknown codes use the existing not-found convention.
- Apply status checks in the API query/service, not only in the view or frontend. Review cache headers so a previously Active tag is not served as valid after voiding.

## Persistence and transaction notes

- Preserve the current CHECK and FK if present in the active database. Test directly that an `Active` tag cannot be saved without `activation_evidence_id`.
- Add a new forward-only migration for the nullable evidence-to-crab reference and FK, after checking existing data. Existing rows remain null. Do not fabricate evidence or rewrite old migrations.
- If data violates a required constraint, stop the migration and report the offending rows for manual reconciliation.
- Serialize activation and void/replacement writes with the existing `IAuditLog` lock and transaction conventions. Keep the existing unique code constraint as the final concurrency guard.

## Verification plan

- Backend/API tests cover label scope and URL configuration, tag list pagination, evidence media/source/object/status validation, reviewer decisions for Watch, activation replay and concurrency, direct SQL CHECK/FK behavior, void/replacement rollback and code collisions, and direct trace requests for Printed, Active, Void, and unknown codes.
- Run the backend solution test command requested in the brief. Record actual command, result, and any unrelated baseline failures.
- This phase does not claim that physical printers or device cameras were tested. Web/mobile and visual print preview are deferred to their follow-up phase.

## Later phase

- Web: multi-select and print 40 × 30 mm labels from the real API, plus void/replace management controls.
- Mobile: paged list of Printed tags, reuse KH-07 camera/upload, show review pending for Watch/Flagged, activate only after Accepted, and refresh after success.
- Validate the print layout at preview/PDF and run relevant web/mobile checks in that phase.
